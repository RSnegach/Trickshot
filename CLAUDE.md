## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).

## Project notes

Workflow
- Compile check without the editor: the open editor holds `Temp/UnityLockfile`, so batchmode is out. `dotnet <sdk>/Roslyn/bincore/csc.dll -target:library -langversion:9.0 -recurse:Assets/Scripts/*.cs` referencing every `Editor/Data/Managed/UnityEngine/UnityEngine*.dll`, `Editor/Data/NetStandard/ref/2.1.0/netstandard.dll` and `Library/ScriptAssemblies/Unity.InputSystem.dll` builds the whole runtime assembly (Unity 6000.4.1f1 under `C:/Program Files/Unity/Hub/Editor`). Steam code is behind `TRICKSHOT_STEAM`, so no Steamworks reference is needed.
- Just run `bash docs/compile-check.sh` - it already resolves `<sdk>` (the DOTNET sdk, `C:/Program Files/dotnet/sdk/<ver>/Roslyn/bincore/csc.dll`, NOT anything under Unity's `Editor/Data`) and passes every reference. Build the argument list through a RESPONSE FILE or quote each `-r:`; an unquoted `$REFS` splits on the space in "Program Files" and reports every reference as a missing SOURCE file (`error CS2001`).
- Scripts are CRLF (`core.autocrlf=true`); keep them CRLF when writing files programmatically.
- "Add to ideas" means a bullet under `## Ideas so far` in `DESIGN_NOTES.md`, ending with its "just an idea, not being built yet" line. Record it; don't build it.
- Cosmetic renders: in play mode `Trickshot.CosmeticGallery.Begin(@"<dir>", "<filter>")` (filter = job id prefix, e.g. `horse_mark`), then `python docs/cosmetics-before/sheet.py <dir> <sheetdir>`. Stop play mode before `refresh_unity` (a domain reload in play throws unrelated FlexNet errors). The kinematic-velocity console errors during capture are pre-existing and harmless.

Verifying UI in the editor
- Unity MCP is ENABLED and the user wants it used. Menu/HUD work is verified by driving the real game: `manage_editor play`, navigate by reflection (each screen's private `_onPicked`/`_onDone`/`_onPractice`/`_onStart` callback, setting `enabled = false` first as the real button does), `ScreenCapture.CaptureScreenshot` in a SEPARATE `execute_code` call (it fires at end of frame), then Read the PNG. The SP chain is Choose(mode) -> StadiumSelectUI -> SpeciesSelectUI -> CustomizeUI -> the mode's setup screen.
- `execute_code`'s compiler is CodeDom (C# 6): no `out var`, no local functions. Pass `compiler: "roslyn"` if newer syntax is needed.
- Unity does NOT see externally-written files on its own; `refresh_unity` reports `refresh_triggered: false`. Force it with `AssetDatabase.Refresh(ForceUpdate)` + `CompilationPipeline.RequestScriptCompilation()`, and check `external_changes_dirty` in `mcpforunity://editor/state` - a reload that started before the write needs a SECOND refresh.
- A console error whose line number does not match the file on disk is a STALE compile from before the write landed, not a real error.
- This catches what a compile pass cannot: an unreadable HUD row, a mis-sized panel. A clean `csc` build says nothing about layout.

Goalkeeper mode
- `SimConfig.KeeperServeInterval` is a settable static (was a const), driven by the pre-match "Shot interval" slider and read live by `ShotServer.Tick`; `KeeperServeIntervalBase` is the default Reset All returns to.

Networking
- `BodyState` snapshot records are fixed-stride with no per-record length, so any per-body wire field forces a `NetCodec.ProtocolVersion` bump (v7 added `erect`). Fields appended AFTER the body loop (e.g. `guided`) are read with `r.More` and need no bump. `InputFrame`'s trailing `bits2` byte is the extension point for new held buttons (bit 4 = thirdLeg).
- A held input bit must be written onto the body every tick (not on edges): the host re-feeds a quiet client's last frame forever, so only a level write lets a release land.
- The discovery probe reply carries only a `mode` STRING (`LobbyProbe`), so new browsable lobby facts go in `NetSession.ModeLabel()` rather than the probe format: Match appends a `[LF:SRC]` tag for the roles the host wants (`LookingRoles.Tag`/`Parse`). `SessionBrowserUI` filters on the parsed mask; an untagged or older label parses to 0.

Ragdoll / cosmetics
- `Bone` is a fixed 13-slot enum shared by every body plan; ~47 `Bone.Count` loops (balance, mass, poses, gait, emotes, replay) assume every slot is body mass. Optional parts (hair, the adult appendage) are Verlet cosmetics parented to a bone, not bones.
- `ActiveRagdoll.IsGrounded` is a pelvis sphere-cast: it reads grounded before touchdown and flickers for a few frames while a landed body settles. Gate air-only input on jump/landing edges (see Striker's `_wheelArmed` / `_airHold`), never on the raw flag.
- The adult hitbox is a compound `CapsuleCollider` under the pelvis rigidbody, adopted via `ActiveRagdoll.RegisterExtraCollider`; self-collision ignores are re-applied on every enable (`IgnoreOwnCollisionsWith`) because PhysX refuses `IgnoreCollision` on a disabled collider. `BoneOf` returns null for it by design; the ball resolves it through `AnatomySim.IsHitbox`.
- `HairSim` uploads mesh vertices in `LateUpdate` behind `_meshDirty`; `Build` must upload vertices BEFORE assigning triangles or Unity rejects the triangles and every card is invisible (static styles never dirty the mesh at all).
- Cosmetics are partial-class files per concern (`Cosmetics.Hair/Facial/Accessories/Hats/Masks/Horse/HorseDecor/Elephant.cs`). Every generated piece goes through `Piece(parent, mesh, mat)` and every material through `Own(...)` with `_rag` set, or it leaks on the customize preview's per-drag rebuild.
- Decor rows in `BodyLayout` are colliders + primitive visuals. `ActiveRagdoll.TryGetDecor(name)` returns a built row's transform and SCALED dims so a cosmetic pass can dress it; `DecorSpec.Hidden` keeps the collider and skips the primitive (elephant ears/tusks), `GirthDims` scales dims by girth on every axis (tusk chords). Horse markings/tack and elephant tack are NOT rows any more; the option lists in `SpeciesCosmetics` still are, and indices are wire state.
- `MeshGen.Param(f, nu, nv)` winds its front face as Cross(du, dv); `Cosmetics.ParamOut` picks the winding from a supplied outward direction. `Lathe` profiles are (radius, y) bottom-to-top with the solid on the left; `Extrude` is centred on z = 0, front face +Z; `Tube` UV is u round, v along.
- `Mathf.SmoothStep(a, b, t)` INTERPOLATES a..b; use `Cosmetics.Smooth(a, b, t)` for a GLSL-style threshold.
- Replays (`ReplaySystem`) record position, rotation AND local scale; `ReplaySystem.TrackBody` adds a body's bones plus its `AnatomySim` pieces and pauses that sim as a driver. Re-run `Setup` after any tracked body is rebuilt.

Match mode (scrim)
- `perSide` is the roster size INCLUDING the keeper (shirt 0 is always the keeper, outfield is `perSide-1`), and "N a side" means that number everywhere: pitch sizing, both team-size pickers, `Footballer.PerSide`. Label a lobby with `perSide` itself - subtracting the keeper for display is what made 3v3 read as 2v2.
- MULTIPLAYER CANNOT SEAT MORE THAN 4 A SIDE. Two teams share the 8-slot board, so `NetSession.ScrimPerSide` clamps to `ScrimSlotsPerTeam` (4) and `SlotAllowed` refuses shirts past it. A picker offering 5 or 11 silently seated 4 and opened a lobby that lied about its size; only offer sizes the board seats, and check the SEATING predicate, not just `SimConfig.Formation`, when adding one. Single player has no such cap (`Max(2, ...)`), so the two pickers legitimately differ.
- `perSide` 1 is not a legal match (a keeper and nobody): the floor of 2 is a shirt invariant re-clamped in `ScrimPerSide`, `Footballer` and `GameBootstrap`. The smallest match is `{GK, ST}`.
- `SimConfig.ApplyMatchStatics` unconditionally resets the goal to regulation and is called by the SINGLE-PLAYER match path only, so a per-match goal size must be re-applied after it. The networked path never calls it and instead writes the host's config on every peer - goal size must stay one number from one peer or the goal-detection plane desyncs.

Setup panels
- `PrematchUI.FootH` reserves a band for Back/Start, but `DrawNav` pins those to the SCREEN bottom, not the panel - so that band is empty plate at the bottom of every setup panel. Accuracy trims it to 18f; the other modes still carry the old height (they were laid out against it).
- Accuracy CHALLENGE hides Reset All: its only control is the keeper Yes/No, which ResetAll does not touch, so the button would do nothing visible.

HUD panels
- Anything drawn OUTSIDE `Hud.PanelStart`'s plate is bare text over the live camera - over the crowd it is unreadable. Put per-run readouts in the panel as extra `Hud.Stat` rows (the row count is passed to PanelStart, so decide it up front) rather than below it.
- `UITheme.Dot` is a square `Fill` wrapped in a wide glow: fine at its 3px default (page dots), but at pip size it reads as a square and the glow bleeds into neighbours. `UITheme.Disc` is the flat antialiased circle to use instead (`Chip` is a rounded SQUARE).

HUD callouts
- `Hud.Flash` is a SMALL stylized pill at the TOP of the screen that hugs its own text, not a big centred callout. `Hud.Banner` (end of round) stays a centred panel - it ends play rather than interrupting it - but takes its accent from the same classifier.
- `Hud.KindOf` colours both: green = goal/save, yellow + flanking `Hud.Star` = epic save, red = every other OUTCOME, neutral grey = the callouts that are not verdicts (`CROSS:`, `REPLAY`, `TIE`, `GAME OVER`, `+n`). Its test ORDER is load-bearing and each rule has a counter-example behind it - failures first, then informational, then epic before plain save, then good/bad. Add new callout words to the right tier, never to the top.
- The live counter-example for rule 1 sitting above rule 2 is MP accuracy's `ALL OUT - ROUND REPLAYED`, which matches BOTH `ALL OUT` (rule 1, red) and `REPLAY` (rule 2, grey); order alone keeps it red. (The older `STRIKE 2 - EPIC SAVE!` example is no longer producible - accuracy callouts are terse now, and both accuracy call sites pass `SaveWatch.Callout(allowEpic: false)` anyway.)
- ACCURACY CALLOUTS ARE TERSE: `GOAL` or `STRIKE n` in the scored modes, `GOAL`/`MISS` in practice (which spends no strike, so it has no number to show). The round number and the strike pips are already permanent HUD rows, so the pill only names the OUTCOME - it used to spell out `ROUND 4 CLEARED` / `STRIKE 2 - MISSED THE TARGET`, which is a sentence to read in 1.6 s while the next round arms. `GOAL` is green via rule 4's `GOAL` test and `STRIKE n` red via rule 1's `StartsWith("STRIKE")`, so the classifier needed no change; `CLEARED` and `ON TARGET` now have no producer at all.

Setup screen template
- `SetupPanel` holds the shared shape of a setup screen, taken from the accuracy PRACTICE screen (the reference layout): `Height(rows)` sizes the plate, `GoalRow` draws the `GoalEditor` picture + keeper row, `Map` puts the placement map in its standard slot right of the panel, and `Begin` draws the scrim/plate/title.
- ONLY `HostSetupUI` currently calls it (Height/GoalRow/Map), which is how MP accuracy came to match SP. `PrematchUI` still draws its own equivalents and has NOT been migrated - moving it onto `SetupPanel` is the obvious next step and would make the two provably identical rather than merely alike. `Begin` has no caller yet.
- `HostSetupUI` draws a SECOND dead-ball map (`DrawFreeKickSetup`) for SET PIECES only. Accuracy draws its own wall-less one inside its branch; leaving accuracy in that guard stacked two maps, the lower one showing a WALL marker the mode does not have.
- MP accuracy has NO standalone goal-size or keeper picker any more: both live on the `GoalEditor` graphic (`yesNo: true`), and its goal rides the wire as two independent scales (`goalScale`/`goalScaleH`) rather than one three-step preset. `_accNoKeeper` is derived from the row's level (`kLvl <= 0`).

Single-player setup screens
- ONE layout for every SP setup screen, and the accuracy practice screen is the reference: the `GoalEditor` picture, the keeper row directly under it, then whatever that mode adds. Anything new goes BELOW the keeper row.
- `GoalEditor.Draw` takes `locked` (regulation size, no drag handles, no Default button - for a scored CHALLENGE, whose score has to mean the same thing every run) and `keeperRow` (`Ladder` = the five named difficulties, `YesNo` = a plain Yes/No). Yes/No stores its answer in the SAME `keeperLevel` int - 0 is None either way, Yes is `GoalEditor.YesLevel` - so no caller needs a second field.
- A LOCKED editor must not have its size stored back into `PrematchUI._goalWidth/_goalHeight`: those are static and shared with practice, so writing regulation there resets a goal the player sized in practice just by opening the challenge screen.

Accuracy mode (practice / challenge)
- SP Accuracy forks on `AccuracyModeUI` into PRACTICE and CHALLENGE, latched in `SimConfig.AccuracyPractice`. CHALLENGE SKIPS the pre-match screen entirely (`GameBootstrap.ShowPrematch` routes Accuracy to the fork; `ShowPrematchPanel` is the old body). Practice's Back returns to the fork, not past it.
- CHALLENGE is the scored game and must be reproducible, so `BuildMode` resets goal size / ball speed / striker speed / wall for it ABOVE `Arena.Build` - that call is what builds the goal frame at the current size, and practice's hand-sized goal would otherwise carry into a scored run. Practice keeps whatever its setup wrote.
- PRACTICE: goal size + keeper (None..Insane, None = no keeper) come from the shared `GoalEditor`; target size and speed are two 0-100 sliders stored as `AccuracyPracticeSize01`/`Speed01`, both spanning the CHALLENGE's own extremes (`AccuracyPracticeRadius()`/`Speed()`), so the two modes can never drift apart. No strikes, no score, no career write.
- Both accuracy modes now open the pre-match panel (`ShowPrematchPanel`), which branches on `SimConfig.AccuracyPractice`: practice gets a draggable goal + the keeper ladder + the two target sliders + the placement map; challenge gets a locked goal + a keeper Yes/No and nothing else. The fork screen itself carries no settings at all.
- NO KEEPER is offered in every accuracy mode via `SimConfig.AccuracyNoKeeper`. It has to be a FLAG, not just "ability 0": Challenge rewrites `KeeperAbility` from the tier ladder every round, so a bare 0 would be gone on the next shot. `AccuracyKeeperAbility` returns 0 flat while it is set. Both screens set it through the goal picture's keeper row - the None..Insane ladder in practice, the Yes/No in the challenge - and `PrematchUI.Apply` writes the flag AND the ability together (`AccuracyNoKeeper = _keeperAbility <= 0.001f`) so they cannot disagree.
- MP carries it as a NEGATIVE `MatchConfig.keeperAbility` (-1 = none): accuracy's real ability comes from the round ladder, so that field was free to overload rather than growing the packet. It only governs the AI keeper - a human who took slot 0 is a player who chose that seat, and an empty slot 0 was always the other way to get an open goal.
- Practice builds its keeper with the ordinary `BuildAiKeeper` guard so None means an open goal; CHALLENGE passes `alwaysBuild: true` because tier 0's 0.01 sits on the guard's threshold - unless `AccuracyNoKeeper`, where neither builds one.
- Practice reopens the placement map in-mode on M (`AccuracyGame.SetMapOpen`), and `AccuracyGame.MapEscapeOwned` is checked by `PauseMenu` so the Escape that closes it does not also pause - the same contract as `GameManager.CrossMapEscapeOwned`. Closing the map re-arms immediately on the new spot.
- `SetPieceMap.DrawSetupPanel`/`Draw` take `showWall` (practice has no wall); the Ball/Wall toggles are still ALLOCATED when hidden, just drawn off-screen, or every control id after them shifts.
- Accuracy has NO live-tunable settings, so `PauseMatchSetup.RowsFor` returns 0 for it and the pause menu's "Match Setup" goes straight back to the full pre-match flow (the Practice/Challenge fork) instead of opening a card. The generic 3-slider default was wrong for it: shot/striker speed are not part of a dead-ball mode, and its keeper ability is owned by the round ladder (Challenge) or the goal picture (Practice), so a slider would be overwritten next round or silently disagree with the picker.
- Accuracy makes a scored run the SAME SHOT for everyone with two paired flags (SP challenge + all of MP; SP practice keeps the player's own build and body). `SkillTree.MaxShootingOverride` forces `shotpower`/`shotacc`/`trap` to their species ceilings; `PlayerProfile.UniformBodyOverride` evaluates every BODY baseline at the default height/weight. Both override a computed RESULT, never the saved tree or profile.
- `UniformBodyOverride` works by overriding `HeightT`/`WeightT`, the normalised slider positions - which is what keeps it stats-only. The visual scale and ragdoll mass read the RAW `Height`/`Weight` (`HeightScale`, `MassMul`), so a big character still looks and weighs big while shooting like the default one. One switch covers shot, move, sprint, jump, push and reach, since all six are functions of those two. `HumanShotPowerMax` is unaffected: `ShotAt` takes its inputs as parameters and the ceiling passes `1f, 1f` explicitly.
- Without the override a 2.05m/110kg build shot at 1.856 against a 1.60m/55kg build's 1.071 (SHO 99 vs 57); with it, every body is 1.328 / SHO 81.
- All three accuracy globals (`MaxShootingOverride`, `UniformBodyOverride`, `SimConfig.HumanKeeperSpeedMul`) are cleared in OnDestroy, or every later mode inherits them.
- A HUMAN keeper in MP accuracy is handicapped twice: `AccuracyBoard.SetVisualHidden(true)` hides the target's DISC from him only (trigger stays live, so scoring is unaffected, and shooters/spectators still see it), and `SimConfig.HumanKeeperSpeedMul = AccuracyKeeperHandicap` (0.75) scales his strafe, jump, lunge, dive AND dash dive. All five paths must be scaled - the dive constants are `const` (a balance contract the AI keeper shares), so the handicap is applied at the point of use. Cleared in OnDestroy like the stat override.
- No EPIC SAVE in accuracy, either mode: `SaveWatch.Callout(allowEpic: false)` collapses it to a plain SAVE. A save there is a STRIKE against the player, so the gold-star highlight celebrated the wrong side of the outcome. Set pieces still get the epic tier.
- ACCURACY NEVER HAS A WALL, in any mode or path. `NetSetPieceMatch` leaves `_wall` null in `AccuracyMode` rather than building one with zero blockers: `SimConfig.WallCount` is a shared mutable static that every `_wall.Build` call site reads live, so "it happens to be 0" is a weaker guarantee. Every `_wall` use there is null-guarded.
- The random shot band is the D: from the front edge of the 18 out to the arc of `PenaltyArcRadius` about the penalty spot. The far edge is an ARC, so a picker chooses x FIRST and draws the depth against `SimConfig.AccuracySpotFarAt(x)`; `AccuracySpotHalfW` is where that arc meets the box edge (7.31m), NOT the arc radius - using the radius pins about a fifth of all spots in a line on the box edge, where the band has no depth.
- SP challenge keeps TWO career bests, `AccuracyBestScore` (with a keeper) and `AccuracyBestScoreNoKeeper`; `CareerStats.AccuracyBest(noKeeper)` picks one. `AccuracyGame` latches `_noKeeper` at Configure alongside `_practice`, so a run is always scored against the board it started on. The with-keeper field keeps its old name so existing saves stay attached to the harder mode.
- The SP CHALLENGE end card (`AccuracyGame.DrawEndCard`) shows rounds cleared / strikes / career best and three buttons: Replay (in-process `BeginRun`, no rebuild), Match Setup and Main Menu (the SAME `System.Action` closures `GameBootstrap` hands the pause menu, injected through `Configure`). PRACTICE never reaches it - `EndRun` is gated on `!_practice` and the practice OnGUI branch returns above it.
- "NEW PERSONAL BEST" needs `_bestBefore`, latched at Configure: `CareerStats.RecordAccuracyRoundEnd` is void and banks the score BEFORE anything reads it back, so after `EndRun` the stored best has already absorbed `_score` and the two can never differ.
- The card is clickable, so it FREES the cursor in `EndRun` and re-captures in `BeginRun`. `PauseMenu.Resume` re-captures unconditionally with no notion of what a mode wanted, so `AccuracyGame.Update` re-asserts `CaptureCursor(false)` on the first unpaused frame while `_cursorFreed`. The card also returns early when `PauseMenu.Paused` - the pause menu offers these same three actions, and two live button sets would both hit-test.
- CHALLENGE: one shot per round from a random spot in the shot band (the D - see above) at ONE patrolling target, and clearing a round needs the ball in the goal AND through the target. Anything else is a strike; three ends the run.
- Difficulty is a pure function of the round number - `SimConfig.AccuracyTier(round)` and the `AccuracyTargetRadius` / `AccuracyTargetSpeed` / `AccuracyKeeperAbility` helpers beside it. Never add a difficulty knob to this mode; change the curve.
- `AccuracyTarget` only patrols when `SetDrift` is called; a bare `Spawn` leaves it parked and bobbing, which is what the menu-scene vignettes rely on. `Patrol` clamps as well as reflects, or a long frame pins the disc flipping at an edge.
- The MP board header is just `STRIKES` / `SUDDEN DEATH`, and a save in accuracy never reads EPIC - both were flowery restatements of what the card already said.
- MP accuracy reuses the shootout wire tally: `scored[]` is rounds cleared and `taken[]` is STRIKES. `ShooterDone` tests `taken >= AccuracyStrikes`, and the shared `_taken++` at the top of `ResolveAttempt` must stay OFF the accuracy path (a cleared round must not spend a strike).
- Two MP formats, from `MatchConfig.accSuddenDeath` (the old `accTurnByTime` slot reused in place; the four retired accuracy fields are still written/read as zero to hold the packet layout). STRIKES = each shooter plays their run out; SUDDEN DEATH = one shot per visit in a shuffled cycle, last standing wins. A cycle that eliminates every survivor at once is VOIDED and replayed (`CloseSuddenDeathCycle`) so a winner is always separated - but only when more than one player went out, since a lone shooter has nobody to outlast.
- FULL TIME draws a results card (`NetSetPieceMatch.DrawAccuracyResults`), not the shared one-line `Hud.Banner`: winner crowned at the top with score + strikes, everyone else beneath. `DrawAccuracyBoard` RETURNS EARLY on `st.over` and hands off to it - the live board and a centred card overlap at any window narrower than the design width. `WinnerSlot()` is the single winner resolver both the card and `WinnerText()` call, so the crown and the headline cannot disagree; it returns -1 for a tie (no crown) and, in sudden death, the SURVIVOR - who can be outscored by someone they outlasted, which is why the crowned slot is pinned to the top of the sort instead of sorting by score.
- The card has NO buttons: `GameBootstrap` leaves both `onRestart` and `onFullSetup` null whenever `Multiplayer.IsActive` (the net protocol has no match reset), so a Replay or Match Setup button there would be dead. Only `ReturnToMainMenu` is passed unconditionally.
- A departed shooter is dropped from `_bodies` on every peer AND has `_taken[i]` overwritten to `Max(ShotsEach, AccuracyStrikes)`, so a leaver's real strike count is not recoverable - do not try to list them.
- Elimination ORDER is not recoverable either (`_accEliminated` is a reset latch, `taken[]` saturates at 3, the cycle order is cleared): sort losers by score, never claim a placing order.
- `BeginTurn` calls `SetUpAccuracyRound` BEFORE placing bodies, so the round's spot is the one everything is positioned against; `BeginAccuracyRound` (mid-turn, strikes format only) is the path that also has to re-place them.

MatchEvent tags (MP)
- `NetSession.BroadcastEvent` carries a bare string with no length limit, and `NetSetPieceMatch.OnMatchEvent` only structurally parses `WHISTLE`, `MISS` and the `ACCOUT:<slot>:<score>` prefix - everything else falls through to `Flash`. So callout wording is free to change, but those three are a command channel: never reword `ACCOUT:`, and never emit a bare `MISS` as a callout (it hits the audio-only early return and never reaches the HUD).
- Goal/miss audio in MP rides on replicated `scored[]`/`taken[]` deltas in `OnShootoutUpdated`, not on the callout text, so retiming or rewording a callout cannot silence a cue.

Multiplayer menu flow
- There is no "Other Modes" catch-all any more. The MP hub lists every networkable mode as its own panel (`MultiplayerHubUI.NetModes`), and picking one IS the mode choice: `HostOrFindUI` (renamed from `OtherModesUI`) is titled with it, `HostSetupUI` takes a `GameMode` and draws NO mode picker, and `SessionBrowserUI` takes one too and lists only that mode's lobbies (matched via `NetSession.LabelIsMode`, which shares `ModeWord` with `ModeLabel` so the label and the filter cannot drift).
- The role filter ("looking to play as") is Match-only in the browser: no other mode advertises roles, so elsewhere the row could only hide rows.

Steam (all of it is a STUB)
- There is NO Steamworks SDK in this project: no package, no `Assets/Plugins`, no appid, and `scriptingDefineSymbols` is EMPTY - so `TRICKSHOT_STEAM` is never defined and `SteamTransport.Available` is always false. Every Steam call is a documented `TODO(steam)` behind that define. Never describe a Steam feature as working; the go-live checklist is in `MULTIPLAYER.md`.
- Consequently the game always runs on `DirectIpTransport` (or loopback), and `Multiplayer.SteamLinked` is false everywhere. A UI that only appears when Steam is linked is a UI nobody can currently see - put host-facing features on BOTH transport paths.
- `SteamFriendsAPI` owns friends + invites: `RequestFriendsList`, `InviteToLobby(friendId)` (the whole invite feature is one `SteamMatchmaking.InviteUserToLobby` call - no overlay needed), `OpenInviteDialog` (overlay fallback), and `CanInvite`/`CurrentLobbyId`. It reads the lobby id LIVE off `SteamTransport.LobbyId` rather than caching one, so it cannot outlive its session.
- `SteamTransport.LobbyId` must be assigned from the `LobbyCreated_t` / `LobbyEnter_t` CALLBACKS, never inline: `CreateLobby` is async and an invite sent against a zero id silently does nothing. `Shutdown` clears it unconditionally.
- `InviteToLobby` returns bool and the UI SHOWS a false as "Failed" per row: Steam's own send can fail (invites blocked, lobby full, stale id), and a silent failure is indistinguishable from being ignored. `SteamFriendsAPI.AppId` is 480 (Valve's Spacewar test app) until the real one exists, or a friend in any other game reads as playing Trickshot.
- `InviteFriendsUI` is the in-game friend picker opened from the lobby's "Invite Friends" (host only, both transports). Static class, drawn LAST by `LobbyUI` so it sits over the roster.

IMGUI modal rules (learned the hard way)
- Every control must be allocated on EVERY event pass, or ids shift between Layout and Repaint and every click on the screen breaks. So: LATCH a close request and act on it after drawing, never `return` early out of a half-drawn panel; and disable a conditional button with `GUI.enabled` rather than skipping it.
- `UITheme.ClickBlocker(w, h, keep, keep2)` is the modal's click guard and must be called unconditionally - it moves itself off-screen for the hole rather than skipping the control.

Striker-mode crosser (MP)
- The crosser body is a child `Body` object of the `Crosser` and is rebuilt per seat holder by `NetStrikerMatch.RebuildCrosserBody` (a human's roster look, or the orange AI); `Crosser.SetRagdoll` re-points the driver. Single-player's `BuildStrikerMode` still puts the ragdoll on the Crosser object itself, so never destroy `Crosser.Ragdoll.gameObject` without checking it is not the Crosser's own.
- The host's crosser dropdown reads the roster (humans always, AI seats while a human crosses; an AI pick is `NetSession.AssignCrosserAi`, a seat swap). The open list is modal and opens downward: IMGUI gives an overlapping click to the first-drawn control, which is how the AI sliders once ate every pick.

Menu scene panels (live mode vignettes)
- The Single Player / Multiplayer submenus render a live ragdoll vignette per mode into each panel (`Assets/Scripts/Play/MenuScenes/`): `MenuSceneStage` owns a disabled camera, one `RenderTexture` per panel and the shared globals; `MenuScene` subclasses are one per mode; `ModeGrid` is the paged grid both submenus draw; `ScriptedInput` drives the REAL `Striker` through a scripted `IStrikerInput`.
- Sub-stages sit at POSITIVE z (3000 + 120 each) on x = 0. Positive because `BallController`'s under-crossbar cap solves `Sign(ballVz) * Abs(AttackGoalCenter.z)`; on-axis because `KickDetector`'s bicycle bonus and `DefensiveWall`'s facing steer by the direction to the readonly `SimConfig.GoalCenter`.
- `BecomeDisplayBody` does NOT stop `ActiveRagdoll.FixedUpdate`, `HairSim` or `AnatomySim`. Freezing a scene must also set `enabled = false` on the ragdoll and those sims, or idle panels keep paying full solver cost.
- `Goalkeeper` reads a ball as incoming only when it travels AGAINST `outSign` (`closing = ballVz * -out`). A wrong sign means he never reacts and NOTHING errors - the hardest bug in this area to see.
- He dives only when the offset beats his DEAD BAND: `KeeperStrafeSpeed * lerp(0.45, 2.0, ability) * 0.55 * timeRemaining` (~4.2 m/s of reach at ability 0.6). Inside it he sidesteps. Choose aim/flight-time against that, don't guess. Save branches: mid band 1.0-1.7 m + past dead band = layout dive; low + inside `AiKeeperSplayReach` = grounded splay; low + inside `AiKeeperSplitWidth` = planted spread (deliberately NOT the dive state); slow + chest-high + inside `KeeperClaimReach` under the chest speed ceiling = a catch.
- `Striker` air-pitch scroll is consumed ONLY on genuinely airborne frames; the pelvis probe reports grounded well into the rise, so scroll sent then is silently discarded. Same reason a slide/jump must never gate on the raw `IsGrounded`.
- `Striker.IgnoreAcrobat` (added for these scenes) forces the tipped-landing tumble regardless of the player's Acrobat perk, which otherwise lands him on his feet.
- `DefensiveWall.BuildFacing` (added) takes an explicit shot direction; both older `Build` overloads orient off `SimConfig.GoalCenter` and put the wall BEHIND a taker on an off-pitch stage.
- A `Striker`'s slide travels along its facing YAW, never its velocity, so a scripted tackle must aim at an INTERCEPT of a moving target, not at where the target stands.
- Ambient is a global the menu does not own (title reel's sky ambient on one screen, `PlayerPreview`'s raised value on another). `MenuSceneStage` pins it around each render and restores it, or the same figure renders correctly on one submenu and blown white on the other.
- `MenuUI.OnGUI` re-latches panel hover from the REAL mouse every frame: when testing, disable the `MenuUI` component before driving `MenuSceneStage.SetHover` by reflection, or the test hover is overwritten instantly.
- Materials leak per scene open unless freed at the source; `AccuracyTarget`, `DefensiveWall`, `BallController` and `ActiveRagdoll` (gloves + slick physics material) now free their own, since a scene cannot reach those private fields.

Trickshot Cup (Assets/Scripts/Cup/; design in `docs/trickshot-cup-design.md`; build runbook in `docs/cup-build/README.md`)
- Names: Solo (SP), Head to Head (MP), Co-op (MP). A ROUND is one match between two nations; the five bracket levels are STAGES (Round of 32 .. Final). Never "tie" in code or UI.
- `CupRound` is the pure round RECORD (CupBracket.cs); the driver is `CupRoundDriver` (partial: .Kick/.Scene/.Debug). `RoundLine` (CupRoundRules) is the kick sequence and the only source of scores / next kicker (`RefreshFromLine`); never cache them elsewhere.
- Everything seeded comes from `SeededRng` (xorshift, integer-derived floats) forked through `CupSalts`: the draw, coin faces, free-kick spots, dejection variants, loser poses. Peers never sync those, only played results. `CupSelfTest` (menu Trickshot > Cup > Run self-test, or `dotnet run` in `docs/cup-build/cuptest`) checks the pure core.
- Armed -> Live triggers on ball speed > 2.5 OR the taker reporting `Struck` OR the ball 30 cm off its spot. The kick clock (`CupTuning.KickClock`, 30 s) must never run past a launch: the weak auto-shot at zero resets the ball and wipes the real result (that was the "goal counted as a miss" bug). The clock is INVISIBLE by design: nothing draws a dial, a number or a warning as it runs down (`CupHud.DrawMeterAndClock` draws only the power meter), so `KickClock` is the one number to change and no HUD work follows from changing it.
- ANY timed shooting mode's expiry watchdog must gate on `SetPieceTaker.AttemptInFlight`, never on the clock alone. A player who releases on the last tick is still `Charging` when the clock hits zero with the strike a frame or two away, so firing the substitute shot there resets the ball and scores a goal-bound kick as a miss. Only a taker who never engaged times out at zero; one mid-attempt gets a generous absolute grace (the cup's `AttemptGrace`, 6 s) and the ball is then judged by the normal in-flight path. `NetSetPieceMatch` gates its AFK timeout on the same signal (`!_taker.HasCharged`); a sub-threshold tap clears `HasCharged`, so brushing the key still times out.
- Goal = the physics-rate line-crossing latch (`CupSpots.CrossedGoalLine` in the driver's FixedUpdate) OR the other set-piece modes' `BallFullyInGoal` box test. A wall stop reads SAVED.
- Keepers hold the line before the strike: `KeeperController.HoldLine/HoldLineZ` and `Goalkeeper.HoldLine`, set by the driver for Placing / WhistleRaise / Armed, cleared at Live.
- PauseMenu: `Paused` = the menu is up (gate LOCAL input on it); `Frozen` = `Paused && !Overlay` (gate sim / clock / camera on it); `Overlay` is true in networked cup styles (GameBootstrap.BuildMode sets it, TearDownMatch clears it). `SetCupLabels` relabels the single quit entry per style.
- Emote wire ids appended: TrophyLift=33, DejectKnees=34, DejectHips=35, DejectFall=36, WhistleRaise=37; none on the wheel Pages. DejectFall only poses the arms; the choreography frees the body at 0.8 s.
- Coin toss: the face shown always derives from the seeded first kicker + the official caller's call (`CupRoundRules.FirstKickerFromCall`); the coin flies a scripted 9.81 arc because the project's gravity is doubled (-19.6) and a physics arc left the wide shot.
- The arms-round-shoulders lineup pose only holds if neighbours ignore each other's colliders (PhysX folds both arms up otherwise); one arm high over the shoulder, the other low round the back.
- Statics the cup borrows (KeeperAbility per stage, regulation goal, WallCount/Distance, PenaltyMode, `SkillTree.MaxShootingOverride`, `PlayerProfile.UniformBodyOverride`) are written by `CupDirector.ApplyCupStatics` ABOVE `Arena.Build` and restored in the director's OnDestroy. `SimConfig.KeeperAbility` is written per kick.
- Wire: `MatchConfig.cupStyle/cupFormat` after `goalScaleH`, read unconditionally; `NetCodec.ProtocolVersion` 8; `NetRole.Entrant`; every cup slot 0..7 is an entrant (no crosser seat, no AI seats - the field is filled from the nation pool, not from Clankers).
- The referee is a Human-species AI body in the `JerseyDesigns` "Referee" design (ClassicKits) with black limbs, ball collisions ignored; he raises a hand 0.4 s before EVERY `PlayWhistle`. The cup driver owns whistle timing.
- Screens register with `CupDirector.AddGuiHook` and call intents only; the director is `CupDirector.Instance`. Head to Head human-vs-AI rounds run LOCALLY on the owner (Local authority); human-vs-human rounds and all of Co-op run on the host.
- `Hud.Flash` takes a `top` argument; the cup passes 130 so callouts sit under its scoreboard.
- The cup's replay ring is FROZEN at the verdict (`_replay.enabled = false`, `_ringFrozen`) so the kick survives the 5 s scored window, and `StartReplay` must call `ReplaySystem.Play` BEFORE re-enabling the component. `ReplaySystem` only records in `FixedUpdate` while enabled, and `Play` latches recording off itself; re-enabling first appends stills of the aftermath to the same ring and evicts the goal from a 150-frame buffer - that was "the replay runs but never shows the goal", in every style.
- SOLO ONLY, a click cuts a walking cinematic short (`CupRoundDriver.CanSkipChoreography` / `SkipChoreography`): the AI taker's walk to the spot (Placing) and the beaten shooter's walk back (WalkBack, penalties only - Free Kicks' WalkBack is a dejection performance, not transit). It lands every walk on its mark through `CupChoreo.LandAllWalks` (which runs the real `Arrive`, so the lineup pose and arrival flags fire) rather than just cutting the timer, or a body is left stranded mid-stride. It is deliberately UNPROMPTED - `CupHud.DrawSkipTexts` captions only the replay and the celebration windows; do not add one. Networked styles are excluded: these beats are shared screen time on the host's clock.
- FREE KICKS have no lineup and no walk-in / walk-back: every taker starts at the run-up mark; the non-playing bodies stand scattered on seeded per-kick marks (`CupSpots.FreeKickMarks`, 3-8 m behind the ball for the taker's side, 10-14 m back for the other) that must never sit on the spot or the run-up path (a body touching the dead ball under `SetPieceShot` re-launches it at full power). A missed/saved free kick is a 3 s dejection on the spot (`RoundPhase.WalkBack` doubles as that beat); a goal frees the WHOLE scoring side for the scored window. Penalties keep the box-edge lineup choreography.
- The kick clock is zeroed on the Armed -> Live edge (`SetKickClock(0)`); `SetPieceTaker.Begin` takes a one-call `ChargeGate` so a Space already held at the whistle charges from the whistle instead of being swallowed by the stale-actuation guard (that guard was the free-kick "clock keeps running" bug). The rest / 6 s verdicts wait while the ball is still `approaching` the goal (moving toward it above `CupTuning.LiveApproachSpeed`, not fully over), under a 20 s hard cap.
- Podium: the trophy is a `Cosmetics.Piece` on the LEFT forearm (the `AddGlove` offset), losers are kinematic display bodies in `CupPoses.LoserPose` variants (solver off), the champion's wheel page is Lift/Wave/Salute/Point/Thinker with the trophy arm held aloft in LateUpdate. The Co-op trophy lift teleports the team to the centre circle under its first cut (the training pitch's centre is 52 m from the goal, too far to jog).
- The menu vignette (`CupScene`, a `DeadBallScene`) compresses the spot to 9 m and aims 2.9 m wide because `Goalkeeper` reads the mutable `SimConfig.GoalWidth`, which `MenuSceneStage` does not pin; the keeper is a real `Goalkeeper` (outSign -1, HoldLine until the strike) that commits a low dive and is beaten by ~1 m.
- The penalty camera (`CupPenaltyCam`) is CENTRED on the ball-to-goal axis (no side offset), 4 m behind the taker at his run-up mark (7 m behind the ball) and 2.4 m up so the line to the goal clears his head; the FOV solves for the posts near the frame edges with the ball in view.
- A kick line has a WIRE CAP, `CupTuning.MaxKicksInLine` (30 = 2*KicksEach + 2*SimMaxSuddenDeathPairs). Sudden death is unbounded in the rules and `CupState` carries every played line in ONE reliable datagram that `DirectIpTransport` never fragments, so the cap is enforced at both ends: `CupRoundRules.Validate` takes it as `maxKicks` (passed by the host's `CupDirector.ApplyRoundResult` and a client's `CupRoundDriver.ApplyState`; omitted = no limit, tests only), and `CupRoundDriver.CapOutcome` overrides the last allowed kick so a live line always ends DECIDED - `CupBracket.SetResult` accepts nothing else. Keep `CupNet.SizeOf` honest when adding a replicated field (721 B at the cap today).
- `CupEscape.Owned` is the aggregate PauseMenu checks so a cup overlay's Escape does not also open the pause menu. The emote wheel is in it via `CupEmoteWheel.AnyOpen`, an EXPIRING stamp (`KeepAlive` republished each frame by CupHud / CupPodium / CupTrophyLift) rather than a reference count - none of the three closes its wheel in OnDestroy, and a leaked count would swallow Escape for the whole session. The window also covers the frame between an owner's close and PauseMenu's raw key read.
- A remote human's wire emote is validated with `Celebration.OnWheel(id)`, never a `<= WhistleRaise` range test: the cup's five choreography emotes are the TOP of the enum, so a range bound hands a teammate the driver's own 4 s dejections.
- Client puppets are posed by `CupRoundDriver.ApplyBodyPose`, which uses `DisplayAnim` off `BodyState.anim` (emote outranks gait; Idle at rest still snaps) - the same path the other net drivers use. `CupSpectatorView` does NOT yet: its `CupStreamBody` record carries no anim field, so a lobby spectator still sees sliding statues.
- Only Host / Local authority ever runs `SimTick`, and `NetInput` is assigned only when `Authority == Host`, so a client puppet can never reach `Celebration.Play` through the freed-body path. Head to Head's `HandSlotToAi` (host rounds) and Co-op's `HumanLeft` (every peer) are the two leaver paths and are gated by style so they never both run on one round.

## Session Clearing Protocol

Trigger phrases (from the user, in any phrasing): "about to clear", "clearing", "I'm going to clear", "clear soon", or any other indication the user is about to clear/reset the Claude Code conversation.

When triggered, perform a knowledge preservation pass automatically, without asking for confirmation, before the session is cleared. Do not merely acknowledge the clear — do the pass.

**A. Preserve durable project knowledge.** Review the current session for knowledge genuinely useful across *future* Trickshot sessions: architecture and subsystem ownership, important class/file relationships, non-obvious execution paths, project-specific conventions, design assumptions, fragile dependencies or execution-order requirements, physics/networking constraints, recurring gotchas, repository-specific commands/workflows, decisions future agents should consistently follow. Merge only this into this CLAUDE.md.

Rules for the merge:
- Preserve all existing content; do not overwrite unrelated sections.
- Do not duplicate information already present.
- Keep additions concise, high-signal, short factual bullets.
- Never turn this file into a session diary or log of what happened.
- Never save temporary debugging detail or speculation/unverified assumptions.
- Never save facts trivially rediscoverable from source (file lists, obvious structure).
- Correct existing content only when the session definitively proved it wrong.
- Keep the file lean — prune superseded bullets rather than letting it grow indefinitely.

**B. Preserve current task state.** If the active task is unfinished, mid-debug, or otherwise carries short-term context that would be expensive to reconstruct after clearing, write/update `docs/claude-handoff.md` with only: current task; desired end state / acceptance criteria; what's already implemented or changed; key files/classes/methods involved; current build/test/runtime state; known bugs or open questions; approaches already tried that failed, and why; decisions already made; exact recommended next steps. Keep it tight enough that a fresh session can resume cold.

If the task is fully complete with nothing transient to preserve, delete an obsolete `docs/claude-handoff.md` instead of leaving stale instructions behind.

**C. Verify before finishing.** Re-read the changes. Confirm: speculation wasn't saved as fact; durable knowledge landed in CLAUDE.md and only transient task state landed in the handoff doc; existing content survived; nothing verbose or redundant was added; no stale handoff remains for a completed task.

**Report back, briefly:** what durable knowledge was preserved, what task state was preserved, which files were touched, and whether it's safe to clear.

**Scope guard:** this pass may only edit this CLAUDE.md and `docs/claude-handoff.md`. Never touch gameplay code, assets, scenes, prefabs, or project configuration during a preservation pass unless separately asked.
